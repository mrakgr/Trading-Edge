# Lightspeed Connect API — notes

Companion to `ibkr_api.md` and `tradezero_api.md`. Lightspeed sales set up a demo (paper) account on
request (email, 2026-09-14); the key lives in `~/.config/lightspeed-connect/credentials` (`KEY`, mode 600).
§L1 is a pre-read of the documentation (2026-09-15, UNTESTED); measured sections follow.

The documentation is published as markdown for assistants: `https://lightspeed-connect.connecttrade.com/llms.txt`
(index) and `.../llms-full.txt` (everything, 134 KB); each browser page `/developers/documentation/<x>` is
`/docs/<x>.md`. Read the whole thing without a login.

## §L1 What the documentation says (read 09-15)

**Model:** ONE long-lived WebSocket per API key carrying JSON messages both ways, FIX vocabulary with
JSON field names (`OrderSingle`, `ExecutionReport`, `OrigClientOrderID`, `LeavesQty`, `TimeInForce`).
Closer to IBKR's one-socket stream than to TradeZero's REST, but with explicit per-request acknowledgements
(every request gets an `*Update` echo with `ErrorCode`/`ErrorText`) — so it is the best of both: a stream
for fills, a reply for every request. Equities and equity options only (multi-leg up to 4 legs).

| item | value |
|---|---|
| endpoints | paper `wss://onboarding.connecttrade.com:28052`; production `wss://gateway.connecttrade.com:37382` (both AWS us-east-1 NLBs) |
| hours | paper Mon–Fri 04:00–20:00 ET; production 04:00–21:00 ET. **Measured 09-15:** at 03:15 ET both endpoints close the TCP connection at the HTTP upgrade (listeners down outside hours). From 04:00 ET the sockets open in ~0.4 s, but the PAPER engine answered every logon 04:07–05:04 ET with WebSocket close 1013 "try again later — destination unavailable", while PRODUCTION answered an invalid key with `Logout 120` in 0.54 s ⇒ the paper engine itself was down that morning, independent of our key. Diagnostic to keep: a deliberately invalid key separates "engine down" (1013) from "key wrong" (120) |
| auth | socket opens unauthenticated; first message `{"MsgType":"Logon","ApiKey":...}`; reply `Logon` with `SessionId` (UUID) + `ErrorCode 0 "Trading OK"`; **`351 "Trading disconnected"` is ALSO a successful logon** (upstream down, orders reject with 351 until it recovers); a failed logon is a `Logout` (118 no key, 120 invalid key / key in use) and the socket closes |
| keys | per environment, do not expire, ONE live connection per key ("ApiKey in use already"), several keys per account for parallel connections; revealable any time in the platform's API Keys page |
| session | `SessionId` required on EVERY message after logon; a wrong one on a heartbeat reply = error 300 + socket closed |
| logon sequence | open-order snapshot FIRST (`OrderSingleStatus` / `OrderMultilegStatus`, one per open order), THEN the `Logon` reply (= "snapshot complete, you may trade"), then `AccountBalanceStatus` + `PositionStatus` "shortly after" on their own schedule |
| heartbeat | server → client every 60 s; reply optional (the shipped clients echo it with `SessionId`); a client heartbeat with `TestReqID` is answered |
| reconnection | a drop ends the session; on reconnect the snapshot replays CURRENT state only — **messages raised while disconnected are not stored or resent** (same as IBKR's socket, unlike TradeZero's REST rows). Engine restart = broadcast `Logout 299`, log on again |
| identifiers | `ClientOrderID` 16–32 chars, unique within the trading day, on every order/cancel/replace (a cancel carries its OWN new `ClientOrderID` plus `OrigClientOrderID`); broker `OrderID` `O-…`, `ExecID` `E-…` (`##:` prefix = generated by the API layer, not the broker); `RefClientOrderID` = the head of a replace chain |
| numbers | prices/quantities are STRINGS (`"Price":"20.5"`); `ErrorCode` is a number; the balance/position payloads are raw numbers passed through from upstream; timestamps UTC `YYYYMMDD-HH:MM:SS.sss` |
| frame limit | 9,999 bytes per message (`MsgError` code 1 above that) |
| place | `OrderSingle {ClientID, Account, ClientOrderID, Symbol, Side BUY/SELL/SELL_SHORT, OrderType, OrderQty, Price?, StopPrice?, TimeInForce?, ExchangeDestination?, SessionId}`; `Account` is REPLACED server-side by the account bound to the key; `ClientID` = `LSCO` in production |
| order types | `MARKET, LIMIT, STOP, STOP_LIMIT, MARKET_ON_CLOSE, LIMIT_ON_CLOSE`; MOO/LOO = MARKET/LIMIT + `TimeInForce AT_THE_OPENING`; trailing stop = MARKET + `ExecInstruction TRAILING_STOP_PEG` + `PegDifference`. "Additional order types are available on request." **No post-only, no peg-to-touch/mid, no display-size field in the schema** (same gap as TradeZero's API, cf. `tradezero_api.md` §T3) |
| TIF | `DAY` (default), `GOOD_TILL_CANCEL`, `AT_THE_OPENING`, `IMMEDIATE_OR_CANCEL`; no FOK, no GTX/extended-hours flag in the schema; "accounts may be restricted to a subset" (error 35) |
| routes | `ExchangeDestination`; equities default `SMART`. Pro routes: `AMEX, NYSEARCA, BATS, BATYSLIM, EDGAROUT, EDGXROUT, NSDQ, NYSE`. Lite routes: `PDQSMART, MNGD (Apex), ARCA`. Options `SMART` only |
| ack | `OrderSingleUpdate` echoing the order with server defaults (`SecurityType COMMON_STOCK`, `NotHeld TRUE`), `ErrorCode 0 "Validated OK"`, `OrderStatus PENDING_NEW`; a rejection is the SAME message with `OrderStatus REJECTED` + the reason (e.g. `200 "##:REJECT - Duplicate ClientOrderID - …"`) — one error per message, validation stops at the first |
| fills | `ExecutionReport` per execution (`LastShares`, `LastPx`, `CumQty`, `AvgPrice`, `LeavesQty`, `ExecType FILL/PARTIAL_FILL`, broker `LastMkt`/`ExecBroker`/`ContraBroker` when present) followed by an `OrderSingleUpdate` with the new `OrderStatus`. Quickstart transcript: `PENDING_NEW → NEW → PositionUpdate → ExecutionReport FILLED → OrderSingleUpdate FILLED` |
| statuses | `PENDING_NEW, NEW, PARTIALLY_FILLED, FILLED, DONE_FOR_DAY, CANCELED, REPLACED, PENDING_CANCEL, PENDING_REPLACE, STOPPED, REJECTED, SUSPENDED, EXPIRED` |
| cancel | `OrderCancel {ClientOrderID(new), OrigClientOrderID}` → `OrderCancelUpdate "Validated OK"` → `OrderSingleUpdate PENDING_CANCEL` → `CANCELED`; failure = `OrderCancelReject` (`CancelRejectResponseTo ORDER_CANCEL`, `CancelRejectReason`, e.g. 1300 "Cancel request rejected during T5"), then an `OrderSingleUpdate` restating the unchanged state. A cancel after the fill is rejected — "check the ExecutionReport first" |
| replace | `OrderReplace {ClientOrderID(new), OrigClientOrderID, OrderQty?, Price?, StopPrice?, TimeInForce?}` — qty/price/stop/TIF only, qty cannot INCREASE (205), type only LIMIT→MARKET (160); ack `OrderReplaceUpdate`; the chain keeps `RefClientOrderID`. **This is the repeg primitive the OMS wants** (TradeZero has no replace: cancel + new POST) |
| account | `AccountUpdate` → `AccountBalanceStatus` (`stockBuyingPower`, `dayTradeBuyingPower`, `dayTradeOvernightRegTBuyingPower`, `ttlEquity`, `maintReq`, `pendingOrdersMarginRequirements`, `settledFunds`/`unsettledFunds`, `realizedPL`/`unRealizedPL`, `PDT`) + `PositionStatus` (`positions[]` with `pos`, `posAvgPrice`, `realPl`, `unrealPl`, `dailyPl`). Pushed unsolicited as `AccountBalanceUpdate` / `PositionUpdate` "as state changes, and can also arrive between changes". ⚠ "In paper trading, the request can succeed without returning a balance snapshot" |
| locates | `LocateRequest {Symbol, RequestQty, LocateType "L"}` → `LocateQuote {OfferPx per share, OfferSize, QuoteID}` (quote free, review it) → `LocateOrder {…, Price = quoted OfferPx}` → `LocateExecution` or `LocateOrderReject` (1431+ = broker reason + 1430); then `OrderSingle SELL_SHORT` up to the located qty; locates expire at end of day. ETB/HTB classification = the platform's **ETB Lookup page**, NOT the API (TradeZero has `is-easy-to-borrow`; IBKR has tick 236) |
| rate limits | none documented |
| market data | none in the API |
| shipped client | Python `WS_Adapter` (sync, thread) + `ws_async_adapter.py`; logs on, echoes heartbeats, reconnects with backoff 1→30 s, stamps `SessionId`/`SendingTime`/`ClientOrderID`. Any WebSocket library works — a ClientWebSocket + System.Text.Json F# adapter is the natural port |

**Contrast with the other two.** Versus IBKR: same "one socket, fills are a stream" shape, but every
request is acknowledged by name (no `nextValidId`, no `permId`, no clientId dance), rejections are the
ack itself, and there is no gateway process to babysit. Versus TradeZero: no polling, a real replace
message, and a snapshot-on-connect that tells you when your view is complete; but nothing survives a
disconnect (TradeZero's order rows do), and the paper balance snapshot is "not always available".

**Error codes worth pre-wiring in the adapter:** 35 (TIF not allowed for the account), 120 (key in use =
a stale connection is still holding our key; wait, do not spin), 200 (duplicate id), 201/202 (max qty /
position limit — the paper R16 analogue), 203 (state does not allow the request), 204 (sell mismarked:
SELL vs SELL_SHORT), 299/300/351 (session: log on again / socket closed / upstream down), 404 (order not
found), 1101–1135 (schema: unknown field or value — the docs promise the field name in `ErrorText`).

**Open questions to measure:** the `ClientID` value on the demo account (docs show `MyClientID` in paper
examples, `LSCO` in production); what `Account` the server binds; whether paper fills at the real NBBO
(both IBKR and TradeZero do, `ibkr_api.md` §I5); partial fills; a rejection for an oversized order; the
cancel/replace round trip; ack and fill latency vs TradeZero's ~240/300 ms; whether unknown fields (a
post-only flag) are rejected (1101+) or silently dropped (TradeZero drops them); which TIFs the demo
account allows; whether the demo lists Pro or Lite routes.

## §L2 First paper round, measured (09-15, 10:00 UTC = 06:00 ET, pre-market, AAPL, route SMART)

**Availability.** The paper ENGINE came up at **06:00 ET**, not the documented 04:00: sockets opened from
04:00 but every logon got close 1013 until 05:59; production validated keys the whole time. Treat 06:00 ET
as the paper open until proven otherwise. The demo account: `Account <demo account id>`, `ClientID LIGHTSPEED`
(both from the platform's API Console dropdowns; a wrong `Account "X"` + `ClientID "LSCO"` was ALSO
accepted on an `AccountUpdate` — the server substitutes). Paper balance: $100,000 credit,
`stockBuyingPower` 100,000, `dayTradeBuyingPower` 400,000 (4×), `creditMultiplier` 1.

**Logon sequence as measured:** `AccountBalanceStatus` and `PositionStatus` arrived BEFORE the `Logon`
reply (all three within 1 ms, 0.50 s after connect), not "shortly after" as documented. The adapter must
accept them in either order.

| step | sent → first reply | messages, in order (same ms unless noted) |
|---|---|---|
| market BUY 10 | **118 ms** | `OrderSingleUpdate PENDING_NEW "Validated OK"` → +9 ms `NEW` (broker `OrderID` assigned) → +3 ms `OrderSingleUpdate FILLED` (LastPx 330.87) → +1 ms `ExecutionReport FILL` (`LastMkt KNLI`, `ExecBroker INCA`) → `PositionUpdate` (pos 10, unrealPl already 13.3) → `AccountBalanceUpdate` (stockBP −3,308.7) |
| limit BUY 10 @ 100 | 118 ms | `PENDING_NEW` → +4 ms `NEW`; `AccountBalanceUpdate` stockBP −1,000 (the resting notional is reserved, as at TradeZero) |
| replace price → 101 | 117 ms | `OrderReplaceUpdate "Validated OK"` (status still `NEW`) → +5 ms `OrderSingleUpdate REPLACED` under the **replace's** `ClientOrderID`, same broker `OrderID`; reserve moves by 10 |
| cancel (of the replace id) | 118 ms | `OrderCancelUpdate "Validated OK"` (`OrderStatus REPLACED` = state at ack time) → +3 ms `OrderSingleUpdate CANCELED`, reserve released |
| market BUY 1,000,000 | 119 ms | `PENDING_NEW "Validated OK"` → +1 ms **`OrderSingleStatus REJECTED` with `ErrorCode 0` and EMPTY `ErrorText`** |
| market SELL 10 | 117 ms | `PENDING_NEW` → +4 ms `NEW` → +3 ms `FILLED` 330.64 → `ExecutionReport` → `PositionUpdate` pos 0 realPl −2.30 → `AccountBalanceUpdate` |
| `AccountUpdate` | 119 ms | `AccountBalanceStatus` + `PositionStatus` |

**Findings.**
- **Latency: every request is answered in 117–119 ms, and a market fill is complete 13 ms later** — the
  whole `PENDING_NEW → NEW → FILLED → ExecutionReport → position → balance` burst lands within ~14 ms of
  the ack. From the same WSL desk TradeZero paper took ~240 ms per POST + ~300 ms to the fill, IBKR
  555–903 ms. Lightspeed's server round trip is the smallest of the three (AWS us-east-1 NLB, no
  gateway process).
- **Fills at the real pre-market market:** bought 330.87, sold 330.64 → the round trip cost exactly the
  spread (−$2.30 on 10 sh); the quotes match AAPL's live pre-market. No commission on paper.
- **Fill ordering gotcha:** `OrderSingleUpdate FILLED` arrives 1 ms BEFORE the `ExecutionReport`. Book fills
  from `ExecutionReport` (the one with `ExecID`), treat the status message as the state flag — same
  division as IBKR's `execDetails` vs `orderStatus`.
- **Risk rejection carries NO reason:** the oversized order was rejected as `OrderSingleStatus REJECTED`
  (a *Status* message, not *Update*), `ErrorCode 0`, `ErrorText ""`. Documented codes 201/202 did not
  appear. The adapter must key on `OrderStatus == REJECTED` regardless of `ErrorCode`, and cannot tell
  "too big" from any other risk rejection on paper.
- **Replace chain:** after a replace the live order is addressed by the REPLACE's `ClientOrderID`
  (the cancel had to target it); `RefClientOrderID` on reports keeps the original. The OMS's repeg loop
  therefore rotates the working id on every replace.
- **Balance stream is immediate and consistent:** every fill/place/cancel produced a `PositionUpdate` +
  `AccountBalanceUpdate` pair in the same millisecond, with the resting notional reserved and released
  exactly — the account view can be maintained from the stream alone (TradeZero's totals lagged).
- `Account` is substituted server-side as documented; `ExchangeDestination` defaults to `SMART`.

## §L3 Second paper round: validation, shorts, locates, TIFs, routes (09-15, 06:03 ET)

| probe | result (every reply ≈ 120 ms) |
|---|---|
| `TimeInForce FILL_OR_KILL` | `OrderSingleStatus REJECTED`, **`ErrorCode 106` "##:REJECT - Unknown TimeInForce 'FILL_OR_KILL'"** — schema errors DO carry a code + text (the risk reject in §L2 did not); the `##:` prefix marks the API layer, not the broker |
| unknown field `PostOnly: "TRUE"` | **silently dropped**: accepted `NEW`, the echo lacks the field (same as TradeZero; the documented 1101+ schema codes did not fire). No post-only via the API |
| `ClientOrderID` of 6 chars | **accepted** on paper (the 16–32 rule is not enforced here; obey it anyway for production) |
| bogus symbol `ZZZZQQ`, market | accepted `NEW` and rests forever with no fill ("any symbol is accepted in paper") — a typo will not be rejected, it will sit as an open order |
| `SELL` 5 with NO position | accepted and FILLED → position **−5**: no sell-mismark check (code 204) on paper |
| `SELL_SHORT` 5, no locate, ETB name | FILLED at the bid → **paper does not enforce locates** |
| `LocateRequest` AAPL / GME / ZVZZT | all three: `LocateQuote OfferPx 0.01, OfferSize 100` — a **stub**; paper cannot tell ETB from HTB, so the locate flow can only be tested for message shape here |
| LOO (`LIMIT` + `AT_THE_OPENING`) at 06:03 ET | accepted `NEW`, cancellable |
| `MARKET_ON_CLOSE` at 06:03 ET | accepted `NEW`, cancellable (the default `TimeInForce DAY` is echoed) |
| direct `ExchangeDestination NSDQ`, `IMMEDIATE_OR_CANCEL`, far limit | `PENDING_NEW → NEW → CANCELED` within 1 ms: IOC honoured, direct route accepted |
| limit BUY 330.60 with the bid at 330.64 | rested `NEW` for 10 s, no fill → the simulator fills against the NBBO: buys at the ask (330.87 / 330.91), sells at the bid (330.64), a limit below the bid rests. Pre-market spread on AAPL ≈ 23–27 c |

**P&L bookkeeping gotcha:** after the flattening buy the `PositionUpdate` carried `pos 0, posAvgPrice
330.91, realPl 0` and the balance's `realizedPL` stayed at −2.30 although the second round trip lost a
further −2.70; `ttlEquity` was right (99,995.0) and `stockBuyingPower` reflected the still-resting orders.
As documented, the immediate post-execution position rows carry zeros in the analytic fields — the OMS
must compute realized P&L from its own fills, and use `ttlEquity`/`stockBuyingPower` for capacity.

**Paper's blind spots (things production WILL reject that paper waves through):** oversized ids, unknown
symbols, sell-vs-short marking, locates, position/borrow limits. The one risk reject seen (§L2) came with
no code. ⇒ the adapter's reject handling must be exercised against production's validation layer during
the low-risk live tests the "Going live" page prescribes, not inferred from paper.

**Adapter rules (Lightspeed):** one socket per key, log on, treat the first `Logon` reply as "snapshot
complete", accept balance/position snapshots before OR after it; book fills from `ExecutionReport`
(`ExecID`), states from `OrderSingleUpdate`/`OrderSingleStatus`; a reject is `OrderStatus == REJECTED` on
EITHER message type, `ErrorCode` optional; rotate the working id on every replace (`RefClientOrderID` is
the chain key); mint `ClientOrderID` once, store it before sending; reconnect = rebuild from the snapshot
(nothing is replayed); reply to heartbeats only with the current `SessionId`; frames < 10 KB; paper
opens 06:00 ET (engine), production 04:00 ET.

## §L4 Can an order's status be queried on demand? (09-16, 10:04 ET) — NO

Six candidate message types (`OrderStatusRequest`, `OrderMassStatusRequest`, `OrderStatus`,
`OrderSingleStatus`, `OrderQuery`, `OrderUpdate`) were all refused: `MsgError 1 "MsgType not valid."` or
`100 "##:REJECT - MsgType not found"`. `AccountUpdate` returns balances + positions only, no orders. The
only order read is the logon snapshot: after disconnecting with one limit resting and one market order
filled, the reconnect replayed **the resting limit only** (`OrderSingleStatus NEW 0/10`); the filled order
appeared nowhere — its fill survives only as the position (`PositionStatus` showed AAPL 5) and in whatever
the client logged from the stream before the drop. ⇒ Lightspeed order state is **push-only**: the OMS
must keep its own order ledger keyed by `ClientOrderID`, and after a reconnect reconcile (a) open orders
from the snapshot, (b) everything else from positions vs the ledger. An order that filled during the
outage shows up as a position delta with no execution report.

Cross-broker answer to "place, then query by id": TradeZero **yes** (`GET .../order/{clientOrderId}` at
any time, 404 = never seen; `GET /orders` lists everything incl. filled; the row is the record of truth);
IBKR **partially** (no per-order call; `reqAllOpenOrders` for open, `reqExecutions` for the day's fills by
permId, `reqCompletedOrders` lossy — reconstruct, keyed by `permId`); Lightspeed **no** (snapshot of open
orders at logon, nothing for closed ones). On ALL three, positions are netted per symbol per account: no
broker will say which system's order a share belongs to — attribution lives in the OMS ledger only.
